# 旧版データと安全な差し替え

## 自動で行わないこと

旧版はString ID、旧列名（id/name/body等）、メモリ内H2が既定だった。修正版はLong/BIGSERIAL・event_id/title/message等であり、同じDBへそのまま接続する互換性はない。文字列IDを勝手に数値へ変換したり、旧テーブルを削除して作り直したりしない。Flywayのbaselineやcleanで既存DBを無理に通さない。

ファイルをバックアップしてもDBのバックアップにはならない。元アプリがメモリ内H2で現在も動いている場合、必要データのエクスポート前に停止すると失われる可能性がある。実際の旧接続先は利用者の環境変数次第であり、こちらでは確認していない。

## 既存の本物のデータを移したい場合の確認順

1. 元アプリの実接続先とデータの有無を確認する。投稿本文や資格情報をチャットへ貼らない。
2. PostgreSQLであれば元DBのpg_dumpを取り、別の検証用DBで復元できることを確認する。H2ならH2自身のエクスポートを取得する。
3. 旧ID→新Long IDの対応表を作成し、イベント・人物・作品・参加/出展関係・感想の順に移す。slugは可能な限り維持する。
4. 旧投稿の匿名設定・公開状態・投稿日時を維持し、花びらseedは新しい制約に従って対応を記録する。
5. 件数、FK、匿名、公開/非公開、代表ページ、バックアップからの復元を確認してから公開先を切り替える。

この移行処理と旧DBの調査は今回実行していない。本物の旧DB内容がないため、汎用SQLを自動実行して「移行済み」とはしない。

## フォルダ差し替えの復旧

Install.commandは旧フォルダ全体を隣接バックアップへrenameし、新しいフォルダを配置する。旧DB設定・旧.env・元画像・元文書・未コミットファイルもバックアップ内に残る。新しい状態を別名に退避してから、バックアップのフォルダ名を元に戻せばファイルを戻せる。DBは別に管理されるため、フォルダ名を戻すだけでDB内容が復元されるという意味ではない。

修正版の検証専用DBはポート55433の一時領域。通常DBは55432の永続volumeであり、Verify.commandはそちらを削除しない。
